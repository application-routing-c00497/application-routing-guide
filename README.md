<a id="compare"></a>
## 用同一个任务建立对照

浏览器首页能打开，不代表另一个程序使用的登录、文件或实时通信地址都能访问。先记录失败 App 的具体功能：启动、登录、刷新列表、上传还是播放。选一个不涉及付款或重复提交的小操作，记下时间，然后打开客户端连接记录。

在一分钟内只触发一次该操作，观察是否出现相应目标和错误。记录可能含私人目标参数，保存在自己设备中，不直接截取完整日志发群。若应用会缓存结果，完全退出该应用再启动进行一次对照，不反复清空全部账号数据。

目标是获得“哪个应用、什么操作、什么时间、有没有对应请求”四项事实。不能仅凭任务栏图标或延迟数字认定所有流量已经接入。

<a id="missing"></a>
## 记录里没有请求

首先确认客户端连接记录功能确实已开启，并且普通浏览器请求能够被观察到。若两种请求都看不到，应先核对记录范围，不能从空日志推断 App 绕过了代理。

当浏览器请求可见、失败 App 请求不可见时，检查该 App 是否有自己的代理设置，是否遵循系统代理，以及是否必须重启才能读取新设置。它可能使用独立网络栈，也可能在请求之前就因账户或本地错误停止，不能直接断言需要 TUN。

如果 App 官方提供独立代理选项，按说明核对协议类型和客户端实际监听端口。HTTP 代理与 SOCKS 不是任意互换的；不要随意复制网上端口，也不要把私人订阅 URL 填进代理服务器栏。记录原值后只改这一项，验证一次，无效则恢复。

受组织管理的设备不要覆盖公司代理或自动配置脚本。无法判断某条代理的归属时，先把现象交给管理员，保留正常业务网络。

<a id="routing"></a>
## 请求存在但出站不符合预期

对照失败时刻的目标、命中规则和最终出站。Mihomo 的规则模式依据匹配结果选择出站；全局模式使用 GLOBAL 策略选择的出站，并不自动选择最快节点。先核对 GLOBAL 当前选项，再考虑用同一个小任务做一次短时对照。

测试前记录原模式与策略。若全局可用而规则不可用，保留命中规则和目标这一证据，继续核对规则或自己的覆盖配置。不要据此把所有域名永久改为代理，也不要把整个规则集删除重建。

若两种模式都失败，恢复原模式，再查看错误是否发生在建立节点连接、目标连接或应用返回响应阶段。不同阶段需要不同处理，切换模式不能替代错误分析。

<a id="tun"></a>
## TUN 是否适合这个问题

TUN 使用虚拟接口并依赖路由、DNS、权限和配置。它可以用于处理不遵循系统代理的某些流量，但不是无条件覆盖所有应用的万能开关。先查所用客户端版本的启用条件，不照抄其他软件的菜单。

如果文档明确建议此场景使用 TUN，先保存网络设置并确认有恢复路径，再通过软件正常功能测试。检查是否有其他 VPN 或代理同时接管网络；不要在不知道用途时删除虚拟网卡、改路由或禁用系统保护。

启用后仍只做原来的一个小任务：看请求是否开始出现在记录中、出站是否符合预期、功能是否完成。只出现 VPN 图标并不能说明成功。出现其他网络异常时，先关闭本次测试启用的接管方式并恢复原配置，再核对基础网络。

<a id="application"></a>
## 网络已通但应用仍报错

能够收到应用服务器的明确响应后，要区分网络故障与业务拒绝。账号登录失效、文件类型不支持或权限不足，需要按应用提示处理；不能用频繁更换出口代替重新认证或权限核查。

若仅上传失败，使用不含私人资料的小文件作一次对照，记录文件大小、失败位置和错误；若仅实时语音失败，查看 App 对 UDP、网络权限和连接方式的官方要求，不因网页可用就排除协议差异。没有文档依据时，不随意开放端口或关闭防火墙。

<a id="finish"></a>
## 完成验证与恢复

修复标准是原先失败的 App 原功能成功完成，并且知道哪项单独改动有效。测试结束后恢复不需要的全局模式、独立代理或 TUN 设置；若新设置需要长期保留，记录保留原因与恢复办法。

仍失败时，将应用版本、系统版本、客户端版本、接管方式、故障操作、脱敏错误以及“有无对应连接记录”交给实际支持方。不要上传完整订阅或含凭据的配置。
